# Multi-Agent Adapter System — Design Spec

**Date**: 2026-05-16
**Status**: Approved
**Scope**: Level 2 skill/command adapter generation for Claude, Codex, Copilot, and Antigravity

---

## 1. Problem Statement

The SDD wizard already generates Level 1 governance stubs (dumb redirectors) for all agents. These stubs point agents to `.sdd/` as the source of truth, but they don't teach agents which skills are available or how to invoke them.

The gap:
- No per-skill adapter files are generated for any agent
- `.codex/skills/` is manually maintained — not generated from `.sdd/skills/registry.json`
- All non-Claude `.vscode/agents/` files contain "No description" stubs
- No `.sdd/commands/` registry exists

**Goal**: When the wizard's `final-template` is copied to a target project root, each agent finds locally:
- A dumb governance entrypoint (Level 1 — already exists, not touched)
- Per-skill adapter files teaching the agent about available skills (Level 2 — what we build)

---

## 2. Conceptual Architecture

```
.sdd/                           ← single source of operational truth
├── skills/registry.json        ← skill list (canonical)
├── skills/{name}/skill.yaml    ← skill spec (canonical)
├── commands/registry.json      ← NEW: command routing map
├── commands/{name}/command.yaml ← NEW: per-command routing
└── templates/adapters/         ← NEW: Jinja2 templates per agent
    ├── claude/command.md.tpl
    ├── codex/skill.prompt.md.tpl
    ├── copilot/skill.prompt.md.tpl
    └── antigravity/skill.md.tpl

         ↓  AdapterGenerator (new, called by wizard at final step)

final-template/
├── CLAUDE.md                   ← Level 1 stub (unchanged)
├── AGENTS.md                   ← Level 1 stub for Codex (unchanged)
├── .claude/
│   └── commands/{skill}.md     ← Level 2: per-skill slash command
├── .codex/
│   └── skills/{skill}.prompt.md ← Level 2: per-skill Codex prompt
├── .github/
│   └── prompts/{skill}.prompt.md ← Level 2: per-skill Copilot prompt
└── .gemini/
    └── antigravity/skills/{skill}/SKILL.md ← Level 2: per-skill
```

## 3. Two-Level Design (Governance Contract)

### Level 1 — Dumb Governance Stubs (DO NOT TOUCH)

These files already exist in the wizard output. They are minimal redirectors:

```markdown
# CLAUDE.md (example)
This project is governed by SDD Harness.
Start here: .sdd/agent-instructions.md
```

Level 1 files are intentionally content-free. The agent is forced to read `.sdd/` for governance. They must remain dumb — no mandate content, no skill lists.

### Level 2 — Skill/Command Adapters (WHAT WE BUILD)

Per-skill files generated by `AdapterGenerator`. They do NOT duplicate governance — they reference `.sdd/` and teach the agent the execution protocol for one specific skill.

**Architectural mandate** (to be included in generated `AGENT_ENTRYPOINT.md`):
```
Generated adapter files are NOT sources of governance truth.
If an adapter conflicts with .sdd/, .sdd/ wins.
Agents MUST discover skills via: .sdd/skills/registry.json
```

---

## 4. CLI / Commands / Skills — Separation Mandate

Three distinct layers. No circular dependencies.

```
Agent
  ↓ invokes via slash
Command  (routing only — no logic)
  ↓ routes to
Skill    (governed intent + protocol)
  ↓ executes via
CLI      (low-level primitives)
```

| Layer | Who uses it | What it does |
|---|---|---|
| CLI | humans, CI/CD, runtime | executes primitives (`sdd governance validate`) |
| Command | agent (slash) | receives slash alias, delegates to skill |
| Skill | agent | governs intent, protocol, budget — calls CLI as backend |

**Anti-patterns** (templates must prevent):
- Skill calling another skill directly (circular)
- Command containing logic beyond routing
- Agent composing raw CLI when a matching skill exists

**Rule** encoded in AGENT_ENTRYPOINT:
```
TOOL SELECTION ORDER:
1. Registered skill  →  when intent matches
2. SDD CLI command   →  when no skill matches
3. Project-native    →  when SDD CLI not applicable
4. Raw shell         →  last resort only
```

## 5. `.sdd/commands/` Registry (New)

Commands are slash aliases that route to skills. Separated from skills to preserve the hierarchy:
- Skill = governed intent (what to do + how)
- Command = invocation shortcut (how to enter)

**Structure:**
```
.sdd/commands/
├── registry.json
└── {command-name}/
    └── command.yaml
```

**`registry.json` schema:**
```json
{
  "schema_version": "1.0.0",
  "commands": [
    {
      "id": "diagnose",
      "slash": "/diagnose",
      "routes_to": { "type": "skill", "id": "diagnose" },
      "targets": ["claude", "codex", "copilot", "antigravity"]
    }
  ]
}
```

**`command.yaml` schema:**
```yaml
id: "diagnose"
slash: "/diagnose"
routes_to:
  type: skill
  id: diagnose
args: []
adapter_targets:
  - claude
  - codex
  - copilot
  - antigravity
```

**Rule**: 1 command → 1 skill. Commands have no logic of their own.

## 7. Adapter Templates (Jinja2)

Templates live in `.sdd/templates/adapters/{target}/`. Each receives:
- `skill` — dict from `skill.yaml`
- `mandates` — list (for governance footer)
- `config` — wizard config (language, enforcement_mode)

### Claude: `.claude/commands/{skill.name}.md`

```markdown
---
name: {{ skill.name }}
description: {{ skill.description }}
---

# /{{ skill.name }}

Load and execute SDD skill `{{ skill.name }}`.

## Required steps

1. Read `.sdd/AGENT_ENTRYPOINT.md`
2. Read `.sdd/skills/registry.json`
3. Confirm skill is registered as `{{ skill.name }}`
4. Read `.sdd/skills/{{ skill.name }}/skill.yaml`
5. Follow the skill protocol

## Allowed CLI

{% for cmd in skill.allowed_tools %}
- `{{ cmd }}`
{% endfor %}

## Risk

`{{ skill.risk_score }}` — {{ skill.description }}

## Non-compliance

Do not invent SDD commands.
Do not bypass the skill registry.
Declare degraded mode if `.sdd/skills/registry.json` is unavailable.
```

### Codex: `.codex/skills/{skill.name}.prompt.md`

```markdown
---
description: {{ skill.description }}. Use when: {% for t in skill.when_to_use %}{{ t }}{% if not loop.last %}, {% endif %}{% endfor %}.
mode: agent
---

## Source

`.sdd/skills/{{ skill.name }}/skill.yaml`

## Required behavior

1. Run preflight: `sdd runtime status`
2. Validate governance: `sdd governance validate`
{% if skill.category in ["analysis", "governance"] %}
3. For large inputs: `sdd organize "$QUERY"` before proceeding
{% endif %}
4. Execute: `{{ skill.cli_fallback[0] }}`
5. Return `policy_result` and `next_actions`

## Allowed CLI

{% for cmd in skill.allowed_tools %}
- `{{ cmd }}`
{% endfor %}

## SDD GOVERNANCE

`SDD GOVERNANCE: drift=${status} | governance=${status} | profile={{ skill.name }}`

Agents must prefer `.sdd/source/*` for governance context over compiled artifacts.
```

### Copilot: `.github/prompts/{skill.name}.prompt.md`

```markdown
---
description: {{ skill.description }}
---

Source: `.sdd/skills/{{ skill.name }}/SKILL.md`

Steps:
1. Read `.sdd/AGENT_ENTRYPOINT.md`
2. Read `.sdd/skills/registry.json`
3. Execute: `{{ skill.cli_fallback[0] }}`
4. Return `policy_result` and `next_actions`

Allowed: {% for cmd in skill.allowed_tools %}`{{ cmd }}` {% endfor %}
```

### Antigravity: `.gemini/antigravity/skills/{skill.name}/SKILL.md`

```markdown
---
name: {{ skill.name }}
description: {{ skill.description }}
---

## Source

- `.sdd/skills/{{ skill.name }}/skill.yaml`
- `.sdd/skills/{{ skill.name }}/SKILL.md`

## Invocation

Use when: {% for t in skill.when_to_use %}
- {{ t }}
{% endfor %}

## Required steps

1. Load `.sdd/AGENT_ENTRYPOINT.md`
2. Load `.sdd/skills/registry.json`
3. Follow the SDD skill protocol
4. Use only allowed CLI

## Allowed CLI

{% for cmd in skill.allowed_tools %}
- `{{ cmd }}`
{% endfor %}
```

## 8. "Ask Family" — sdd-organize Pre-step

Skills in the query/analysis family (`diagnose`, `validate-governance`, and Codex skills `sdd-ask`, `sdd-audit`) include a conditional pre-step in their Codex template:

```
If input or query is large (multi-file, multi-context):
  → sdd organize "$QUERY"   (prepares indexed context)
Then proceed with the skill's primary CLI.
```

This formalizes existing ad-hoc behavior in `.codex/skills/sdd-ask.prompt.md` as a canonical template pattern. The condition applies to skills with `category in [analysis, governance]`.

## 9. New Python Package: `sdd_skills`

Extract `SkillEngine` from `packages/core/sdd_runtime/src/sdd_runtime/skills.py` into a dedicated package:

```
packages/features/sdd_skills/
└── src/sdd_skills/
    ├── engine.py      ← SkillEngine (moved from sdd_runtime)
    └── loader.py      ← reads registry.json + skill.yaml
```

**Why**: eliminates coupling between runtime (artifacts, context) and skill execution. `sdd_adapters` depends on `sdd_skills.loader` only, not on the full runtime.

---

## 10. New Python Package: `sdd_adapters`

```
packages/features/sdd_adapters/
└── src/sdd_adapters/
    ├── adapter_generator.py    ← orchestrates generation per target
    ├── template_renderer.py    ← Jinja2 wrapper
    └── skill_loader.py         ← reads skills + commands registries
```

**`AdapterGenerator.generate(output_dir)`**:
1. Load `{output_dir}/.sdd/skills/registry.json` + each `skill.yaml`
2. Load `{output_dir}/.sdd/commands/registry.json` + each `command.yaml`
3. For each target (claude, codex, copilot, antigravity):
   - Render template per skill
   - Write to `{output_dir}/{agent_dir}/{skill_name}.{ext}`
4. Return `AdapterResult` with file list + any errors

## 11. Wizard Integration

`AdapterGenerator` is called as the **final step** in `Phase456Generator`, after `SeedlingsOrchestrator`:

```python
# phase_4_5_6_generator.py — existing final sequence
self.seedlings_orchestrator.generate_all(output_dir)

# NEW: generate Level 2 adapters
adapter_gen = AdapterGenerator(templates_dir=sdd_templates_dir)
adapter_gen.generate(output_dir=output_dir)
```

Input: `output_dir` already contains `.sdd/skills/` from earlier phases.
Output: adapter files written directly into `final-template/`.

No new CLI command is created. Regeneration requires re-running the wizard.

---

## 12. Testing Strategy

1. **Unit**: `AdapterGenerator.generate()` with mock registry → assert file paths + content for all 5 existing skills
2. **Template contract**: each Jinja2 template renders without errors for all 5 skills
3. **Integration**: run wizard full pipeline → verify adapter files appear in `generated/client/build/final-template/`
4. **Synergy check**: verify no adapter file contains governance content (mandates, fingerprints) — adapters reference `.sdd/` only
5. **Regression**: `sdd governance validate` + `sdd test run` green after changes

---

## 13. Out of Scope

- Fixing `.vscode/agents/` stubs (non-Claude agents with "No description") — deferred
- Standalone `sdd adapters generate` CLI command — deferred
- `protocol.md` and `examples.md` per skill in `.sdd/skills/` — deferred
- Behavioral drift detection, cognitive modes, circuit breakers — separate spec
